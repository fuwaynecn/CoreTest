# 题库供给死锁修复设计

- 日期：2026-09-23
- 状态：已确认
- 触发问题：孩子端进入今天训练时提示「已经完成」，实际并未做题

## 1. 问题与根因

### 1.1 现象

2026-09-23，孩子登录后进入今天训练，页面提示已完成，但当天实际没有作答记录。

### 1.2 直接原因

线上数据库 `/opt/math-trainer/data/math-trainer.sqlite` 中当天的正式会话：

| 字段 | 实测值 |
| --- | --- |
| session id | `8bde7a42-80ea-475f-95f9-1480f1726d6e` |
| session_date | 2026-09-23 |
| kind | daily |
| status | in_progress |
| rule_version | phase2c-v2 |
| session_items 行数 | **0** |
| attempts 行数 | 0 |
| composition_snapshot | `{"composition":{"review":5,"weakness":9,"reading":4,"extension":2},"shortages":{"review":5,"weakness":20,"reading":20,"extension":2}}` |

会话状态是 `in_progress`，但题目数为 0。`web/src/app/child/session/[id]/page.tsx` 用
`session.questions.find((item) => !item.answered)` 判断是否还有未答题目；题目数为 0 时该表达式返回
`undefined`，于是落入「已完成」分支，渲染出「今天的训练完成／你认真完成了今天的题目」。
`!question` 把「全部答完」和「一道题都没有」当成了同一件事。

### 1.3 根本原因：两份设计互相冲突

题库供给被两条规则夹在中间，且从未对齐：

- `2026-09-04-question-bank-refresh-design.md` 要求每个「知识点 × 难度」保留至少 8 道启用候选题，不足时补到 12 道。
- 2026-09-05 上线的题干去重规则 `MAX_SIMILAR_ACTIVE = 1` 规定：同一知识点下，去掉数字后题干相同的题只保留 1 道。

于是每个知识点的不同题干数被压在 1～9 种（38 个知识点里有 23 个只有 1～2 种），题库总量锁死在 103 种；
而「同一道具体题 7 天内不重复」的规则要求每天 20 题 × 7 天 = 140 种可用题干。**103 < 140，数学上不可满足，必然耗尽。**

### 1.4 实测证据

| 指标 | 实测值 |
| --- | --- |
| `question_instances` 总行数 | 357 |
| 按 `questionSimilarityKey` 归一后的不同题干数 | **103** |
| 活跃题目数 | 103（与不同题干数相同） |
| 活跃题目中 `lastUsedAt` 在 7 天内的 | **103（全部）** |
| 7 天过滤后可用候选 | **0** |
| 每个知识点的不同题干数 | 1～9 种；23 个知识点只有 1～2 种，仅 1 个达到 8 种 |
| 变式只含数字的模板 | 119 / 123 |
| 变式组合数 `variantPeriod` | 最小 1，中位数 3，最大 3；123/123 均 < 8 |
| 60 个「知识点 × 难度」格子里低于 8 道的 | 60 |

上表中的 123 个模板指线上全部活跃模板，含 3 个 Phase 1 遗留模板；`phase2Catalog` 自身含 120 个模板、
38 个 `skillCode`，是第 3 节供给计量的唯一数据源。

题库刷新记录显示供给已无法自行恢复：

| week_key | generated_count |
| --- | --- |
| 2026-09-21 | 0 |
| 2026-09-14 | 0 |
| 2026-09-07 | 277 |

刷新并未失败，而是每一道候选题在写入前都被 `questionSimilarityKey` 判为重复而跳过。原因：
119/123 个模板的变式只有数字不同，而 `questionSimilarityKey` 会把数字全部替换为 `#`，
所以同一模板的所有数字变式归一成同一个题干形状。

### 1.5 供给逐步饿死的过程

| 日期 | 会话题目数 |
| --- | --- |
| 2026-09-15 | 8 |
| 2026-09-16 | 11 |
| 2026-09-17 | 4 |
| 2026-09-22 | 8 |
| 2026-09-23 | **0** |

### 1.6 伴随发现（本次不修）

- **review 供给受到期日排布限制**：2026-09-23 只有 1 个知识点到期，而每个知识点每次最多 2 道复习题，
  因此 review 最多 2 道/天，低于配额的 5 道/天。
- **reading 候选池恒为 0**：`reading` 类只取「非到期、非 weakness 目标」的 `thinking_habits` 知识点，
  而 5 个 `thinking_habits` 知识点全部是本周 weakness 目标，导致 reading 候选永远为空。
  这是分类优先级问题（weakness 覆盖 reading）。
- 这两项都不会导致会话中断：`selectDailyItems` 会把缺额重新分配给 weakness，再由兜底循环补满。
  它们影响题目组成质量，不影响能否作答。

## 2. 目标与非目标

### 2.1 目标

1. 解除供给死锁，使每天 20 题在 7 天不重复窗口下可持续满足。
2. 供给不足时不再产出 0 题会话。
3. 0 题会话不再显示「已完成」。
4. 把供给约束变成可执行的自动断言，防止同类死锁再次静默发生。

### 2.2 非目标

- 不实现 `2026-09-04` 设计文档的「每格 8～12 题」目标（需 480～720 种题干）。本次按知识点计量，明确延后。
- 不修改 `MAX_SIMILAR_ACTIVE`，不放弃「同一知识点去掉数字后题干相同只保留 1 道」。
- 不修复第 1.6 节的两项伴随发现。
- 不修改 `skill-decimal` 的 domain 取值，不处理 `skill-reading`、`skill-equation` 两个孤儿知识点。
- 不重构模板 schema，不引入多骨架（`stemPatterns`）模型。

## 3. 供给模型与配额

### 3.1 计量单位

供给以「知识点 × 归一题干」计量：对每个知识点，统计其活跃题目按 `questionSimilarityKey(skillId, stem)`
归一后的不同键数量。这正是去重规则实际使用的粒度。

「知识点」的口径统一定义为 **`phase2Catalog` 中出现的 `skillCode`**，共 38 个，与线上
`question_instances` 中有活跃题目的知识点数量一致。供给闸门测试以目录为唯一数据源，与题库刷新逻辑同源；
线上数据库仅用于取证，不作为计量基准。

### 3.2 配额规则

**`phase2Catalog` 中出现的每一个 `skillCode`（共 38 个），至少 6 种不同题干。**

推导依据：

| 约束 | 需求 | 供给（38 × 6 = 228） |
| --- | --- | --- |
| 7 天不重复窗口全局需求 | 20 × 7 = 140 | 228 ≥ 140，余量 88 |
| weakness 类 7 天需求 | 9 × 7 = 63 | 充足 |
| review 类 7 天需求 | 5 × 7 = 35 | 受到期日限制，见 1.6 |
| reading 类 7 天需求 | 4 × 7 = 28 | 受分类优先级限制，见 1.6 |

总量 228 对应 38 个知识点。稳态下 7 天内最多占用 140 种，始终保有 88 种可用余量。

### 3.3 内容缺口

| 每知识点现有题干数 | 知识点个数 | 需补 |
| ---: | ---: | ---: |
| 1 | 10 | 50 |
| 2 | 13 | 52 |
| 3 | 6 | 18 |
| 4 | 4 | 8 |
| 6 | 4 | 0 |
| 9 | 1 | 0 |
| **合计** | **38** | **128** |

需新增约 128 种题干，涉及约 33 个知识点、约 35～40 个模板。

## 4. 内容变式设计规则

### 4.1 实现机制

`variantSpec.variables` 的类型为 `z.array(z.union([z.string(), z.number().finite()]))`，变量名只需匹配
`/^[a-z][a-z0-9_]*$/i`。因此在 `variables` 中增加中文字符串变量并在 `stemPattern` 中引用，
**不需要修改 schema，也不需要修改生成器**。

```ts
// 现状：3 组数字 → 归一后 1 种题干
stemPattern: "口算：{{left}} + {{right}} = ？",
variables: { left: [38, 46, 57], right: [7, 9, 8], answer: [45, 55, 65] },

// 加一个文字维度后：4 种问法 × 3 组数字 → 4 种题干
stemPattern: "{{prompt}}：{{left}} + {{right}} = ？",
variables: { prompt: ["口算", "填空", "验算", "估算"], left: [...], right: [...], answer: [...] },
```

约束：

- 文字变量**不得影响答案**，`answerSpecPattern` 与数字变量的锁步关系必须保持不变。
- 文字变量名必须匹配 `/^[a-z][a-z0-9_]*$/i`，即只能用 ASCII 变量名。
- `selectVariables` 按同一下标推进所有变量，`variantPeriod` 为各变量取值数的 LCM；
  因此新增文字变量会增加总变式数，其取值数即为新增的题干形状数。

### 4.2 按题型设计变式维度

| 题型 | 变式维度 | 示例 |
| --- | --- | --- |
| 应用与建模 | 真实情境 | 「买 3 支笔花了 {{a}} 元」→「称 3 箱水果共 {{a}} 千克」 |
| 图形与空间 | 情境 + 图形描述方式 | 「长方形花坛」→「长方形课桌面」 |
| 数据与统计 | 情境 + 统计对象 | 「班级身高统计表」→「图书角借阅统计表」 |
| 方程与代数 | 情境 + 未知量问法 | 「求 {{x}}」→「问原有多少」 |
| 数与运算 | 不同问法 | 「口算：{{a}}+{{b}}=？」→「填空：{{a}}+{{b}}=（ ）」 |
| 数学思维与习惯 | 不同审题任务 | 「找出多余条件」→「判断单位是否用对」 |

### 4.3 内容质量要求

- 题干表述须符合小学六年级水平，情境须自然，不使用牵强的前缀。
- 数字与情境的搭配不得产生不合理的生活情境。
- 每道变式必须通过 `validateCatalog()` 的自动校验（占位符完整性、答案格式、单位一致性、可解性）。
- 数学正确性与表述质量由人工抽查确认。

## 5. 代码改动

### 5.1 安全网：7 天窗口由硬过滤改为优先级

文件：`web/src/domain/scheduling/select-daily-items.ts`、`web/src/services/training/create-adaptive-session.ts`

现状：`create-adaptive-session.ts` 在选择前直接把 7 天内用过的候选整体过滤掉，候选池为空时产出 0 题会话。

改动：把窗口判断下沉到 `selectDailyItems`，作为**优先级**而非**硬过滤**：

1. 候选仍按现有规则排序（到期晚优先、掌握度弱优先、难度接近优先、最久未做优先）。
2. 分类选择阶段与第一次缺额重分配阶段，**跳过** `lastUsedAt` 落在 7 天窗口内的候选。
3. 最后的兜底补充阶段**允许**使用窗口内候选，仍按最久未做优先。

这样严守 7 天规则的前提下优先用新题；只有在候选确实不足时才复用最久未做的题，而不会产出 0 题会话。
`selectDailyItems` 的输入增加一个可选的时间窗口参数；`create-adaptive-session.ts` 不再预先过滤候选。

### 5.2 区分「0 题」与「已答完」

文件：`web/src/app/child/session/[id]/page.tsx`

在现有 `if (!question)` 分支之前增加题目数为 0 的判断，渲染「今天的题目正在准备中」，
不再渲染「今天的训练完成／你认真完成了今天的题目」。

### 5.3 首页不再为 0 题会话提供误导入口

文件：`web/src/app/child/page.tsx`

题目数为 0 时，不显示「今天安排了 0 道题」与「开始今天的训练」按钮，
改为显示题目正在准备的说明。

## 6. 验证

### 6.1 供给闸门测试

新增测试文件 `web/src/content/question-supply.test.ts`，断言：

1. `phase2Catalog` 中每一个 `skillCode` 至少有 6 种归一题干。
2. 归一题干总量不少于 200。

测试以 `phase2Catalog` 为唯一数据源：遍历全部模板的全部变式（下标 `0 .. variantPeriod(template) - 1`），用 `instantiateTemplateAtIndex` 渲染题干，再套用 `questionSimilarityKey(skillId, stem)` 计数，与题库刷新使用完全相同的口径。测试按知识点输出缺口明细，便于按批补齐内容。

该测试在当前内容下必然失败（现为 103 种），用于驱动内容补齐；内容补齐后转绿并长期防回归。

### 6.2 回归测试

1. 候选池被 7 天窗口清空时，仍产出满额会话，不出现 0 题会话。
2. 题目数为 0 的会话不渲染「已完成」文案。
3. 候选充足时，选择结果与改动前一致（不因安全网而提前复用）。

### 6.3 全量验证

```powershell
npm run verify
npm run test:e2e
```

## 7. 数据修复

按确认结论，代码修复完成后处理当天的 0 题会话：

1. 先把 `/opt/math-trainer/data/math-trainer.sqlite` 备份到 `/opt/math-trainer/backups/`。
2. 删除会话 `8bde7a42-80ea-475f-95f9-1480f1726d6e`（`session_items` 由外键级联删除）。
3. 确认孩子端可重新创建当天训练。

`one_formal_session_per_child_day` 唯一索引保证每个孩子每天只有一条正式会话，因此必须先删除该行才能重建当天训练。

## 8. 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 内容工作量是主体 | 需编写约 128 种新题干，涉及约 35～40 个模板 | 分批补齐，每批跑供给闸门测试与 `validateCatalog()` |
| 内容数学错误 | 自动校验覆盖格式、单位、占位符，不覆盖数学正确性 | 人工抽查；保持数字与答案的既有锁步关系 |
| 安全网掩盖供给不足 | 降级复用会降低「7 天不重复」的实际达成率 | 供给闸门测试确保供给达标；复用仅作为兜底 |
| 变式文字维度不产生新形状 | 若文字变量被写进被归一化掉的文本位置，则不会增加形状 | 闸门测试直接以归一后键计数，可立即发现 |
